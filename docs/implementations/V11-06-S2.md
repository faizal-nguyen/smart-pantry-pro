## 5. Production

**Migration appliquée par l'utilisateur le 27 novembre 2026, avant la fusion** : la politique publiée avec ce code dit que le registre de la découverte est effacé. Le code ne dépend pas de la migration, ni l'inverse. `CREATE OR REPLACE TRIGGER` remet le déclencheur à l'état activé ; aucune migration du dépôt ne le désactive.

**Vérification après application** (éditeur SQL) :

```sql
-- 1. Suppression : registre, catalogue et partage.
SELECT position('recipe_discovery_receipts' IN prosrc) > 0 AS registre,
       position('public.products SET created_by=NULL' IN prosrc) > 0 AS catalogue,
       position('shopping_list_collaborators' IN prosrc) > 0 AS partage
FROM pg_proc WHERE oid = 'private.delete_user_rows(uuid)'::regprocedure;
-- attendu : true, true, true

-- 2. Déclencheur : il ne réagit plus à l'auteur ni à la date de mise à jour.
SELECT position('WHEN' IN pg_get_triggerdef(oid)) > 0 AS filtre FROM pg_trigger
WHERE tgname = 'v10_product_cache' AND tgrelid = 'public.products'::regclass;
-- attendu : true (aucune ligne si ce déclencheur n'existe pas en production)

-- 3. Export : les deux clés, garde et droits inchangés.
SELECT position('recipe_discovery_receipts' IN prosrc) > 0 AS registre,
       position('catalog_contributions' IN prosrc) > 0 AS catalogue,
       position('auth.uid()' IN prosrc) > 0 AS garde,
       has_function_privilege('anon', 'public.export_user_data(uuid)', 'EXECUTE') AS anon_peut_exporter
FROM pg_proc WHERE oid = 'public.export_user_data(uuid)'::regprocedure;
-- attendu : true, true, true, false
```

## 6. Retour arrière

Code : `git revert <commit du lot>`. Base : rejouer les fichiers entiers, tous idempotents, puis le déclencheur d'origine.

```sql
-- private.delete_user_rows : supabase/migrations/20261127120200_v11_06_delete_user_profiles.sql
-- public.export_user_data : supabase/migrations/20261127120300_v11_06_export_user_data.sql
CREATE OR REPLACE TRIGGER v10_product_cache AFTER UPDATE ON public.products
  FOR EACH ROW EXECUTE FUNCTION private.invalidate_stock_caches();
```

Les lignes effacées et les auteurs remis à `NULL` par des demandes déjà traitées ne reviennent pas : c'est l'objet de la demande.

## 8. Signalés, hors de ce lot

- **Réparation du scanner** : conçue lors du plan, non faite ; elle pourra devenir un lot à part.
- **Fichiers orphelins** : une photo déposée depuis un formulaire de produit ensuite annulé, ou remplacée par une autre, reste dans le bucket, comme avant ce lot. La demande de suppression les efface avec les autres photos du compte.
- **Photo d'un produit du catalogue après effacement** : `products.image_url` garde l'adresse d'une photo effacée ; l'image disparaît pour les autres comptes. La vider demanderait une migration.
- **Partage de listes** (`20250818000001`, jamais appliquée en production) : ses lignes ne sont pas exportées, et les articles qu'un membre a ajoutés à la liste partagée d'un compte effacé partiraient en cascade sur une base rejouée.
- **Motif des colonnes de secrets de l'export** (`(^|_)(token|secret|password|api_key)$`, depuis S1) : il ne retire ni `…_token_encrypted` ni `secret_hash`. Aucune table à `user_id` du dépôt n'a de telle colonne : `store_partnerships.api_key_encrypted` n'a pas de `user_id`, et la table part en E8. À élargir si une table en ajoute.
- **Documents historiques** : `docs/OPTIMIZATION-REPORT.md`, `docs/implementations/V11-06-E2a.md` et `PRP/PRP-232-Recipe-Experience-V2.md` citent encore `RecipeBookScanner` ; ce sont des archives, laissées telles quelles.
