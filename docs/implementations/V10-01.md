La boucle courses → stock → recette → repas dispose maintenant de commandes atomiques, d’une identité réutilisable après interruption, de conversions d’unités et d’une annulation contrôlée. Une réussite dépend d’un résultat confirmé ; les erreurs et les résultats incertains restent récupérables.

La migration n’a été appliquée qu’aux bases PostgreSQL jetables de test. Le résultat local ne démontre pas l’état de Supabase en production, de Safari ou de l’iPhone 17 Pro Max.

## 3. Contrat commun et garanties

- `POST /v1/stock/preview` : résolution propriétaire de recette, portions, lots, allocations et manquants explicites.
- `POST /v1/stock/commands` : validation stricte du contrat partagé puis exécution atomique.
- `GET /v1/stock/commands/:id` : récupération du résultat dans l’espace du compte authentifié.

Les types livrés sont `transfer_shopping`, `consume_recipe`, `consume_inventory`, `adjust_inventory`, `undo_stock`, `save_recipe`, `add_catalog_recipe`, `recipe_add_missing` et `plan_recipe`. Chaque intention porte `command_id` UUID, `command_type`, `payload_version: 1` et son payload. [Contrats](../../packages/shared/src/stock-commands.ts), [routes](../../apps/api/src/routes/stock.routes.ts).

La session validée construit un client Supabase utilisateur. La fonction publique est `SECURITY INVOKER`. L’implémentation interne privilégiée dérive `auth.uid()`, vérifie la propriété et ne fait pas confiance à un `user_id` fourni. Les reçus, mouvements et révisions sont lisibles seulement par leur propriétaire, sans écriture directe du rôle authentifié sur ces tables.

Le verrou transactionnel par compte et les verrous de lignes ordonnés protègent les commandes simultanées. La même identité et le même payload renvoient le reçu initial ; un payload différent est refusé. La réponse perdue n’autorise pas une nouvelle consommation. L’annulation conserve les mouvements et annote le journal ; une version de lot modifiée provoque un conflit au lieu de restaurer une quantité absolue périmée.

Les fonctions historiques `consume_inventory_item` et `transfer_inventory` ont aussi été durcies : identité vérifiée, montants positifs, unité contrôlée pour le transfert et verrous. L’ancien writer `create_shopping_from_recipe` n’est plus exécutable par les rôles publics/authentifiés. Ces fonctions historiques ne remplacent pas le journal et l’idempotence des commandes V10.

Les unités reconnues couvrent masse (`mg/g/kg`), volume (`ml/cl/dl/L`) et comptage, avec alias français/anglais. La précision de calcul est bornée à neuf décimales. Les noms sont normalisés de façon cohérente en Unicode côté TypeScript et PostgreSQL, avec une collation ICU neutre pour la casse, notamment `Œ/œ`. L’allocation réserve les lots une fois dans la recette entière et prend d’abord les dates les plus proches. Un contenant, une cuillère, une unité inconnue ou une autre dimension n’est pas converti sans facteur connu. Les ingrédients explicitement déclarés hors inventaire ne sont pas déduits du stock.

## 4. Reprise, sessions et caches

Les intentions en ligne sont enregistrées dans `localStorage` sous `v10-command:<compte>:<intention>` avant envoi. Les erreurs réseau, 5xx et interruptions de session conservent l’identité ; un refus métier garantissant le rollback permet une intention corrigée. Un stockage inaccessible ou corrompu empêche de remplacer silencieusement l’identité. **Il n’existe pas de file hors ligne exécutée automatiquement.**

Le brouillon de recette est conservé sous `v10-draft:<compte>:...`. Une sauvegarde au résultat incertain garde son payload initial et propose de vérifier la sauvegarde. Le formulaire ne se ferme qu’après relecture de la recette et de ses ingrédients.

Un changement de compte annule et retire les queries, réinitialise les vues privées, le cache du résolveur et les notifications, purge les anciens fichiers de travail et remet à zéro la conversation active. Les réponses tardives du compte précédent sont ignorées. Une déconnexion ou expiration préserve les intentions de ce compte jusqu’à reconnexion ; une connexion d’un autre compte retire ses fichiers de travail.

Les préférences cuisine sont désormais lues et écrites sous `v10-personalization:<compte>:cooking` ; l’indicateur d’import vers la mémoire assistant est aussi propre au compte et les requêtes vérifient le compte attendu. Les réponses d’onboarding utilisent un brouillon par compte. Les anciennes valeurs globales `smart-pantry-personalization` et `smart-pantry-onboarding` restent conservées mais inactives : leur propriétaire n’est pas deviné. La section cuisine invite à confirmer les préférences du compte. La synchronisation du profil entre appareils et sa politique nutritionnelle restent dans V10-03.

Le service worker V10 ne met en cache que le shell public, les assets compilés et les icônes. Il ignore les lectures authentifiées, les services externes et toutes les mutations, et purge les anciens caches de l’application. L’accès hors ligne aux données privées et le protocole de synchronisation natif ne sont pas livrés par ce lot.

## 8. Application et reprise opérationnelle

La migration est [20261008151704_v10_reliability_commands.sql](../../supabase/migrations/20261008151704_v10_reliability_commands.sql). Elle a été créée avec la CLI Supabase et ne doit être appliquée qu’au projet Smart Grocery vérifié.

Ordre de livraison préparé :

1. Inspecter le schéma du bon projet, le support ICU, les fonctions existantes, leur propriétaire, les grants et les RLS des tables préexistantes. Sauvegarder les données et vérifier les doublons de bibliothèque catalogue. La migration refuse les divergences détectées et les doublons ; elle ne les supprime pas.
2. Tester la migration avec des comptes séparés sur cet environnement et régénérer les types complets. Le schéma local des tests ne charge pas toute l’histoire des migrations ni un dump de production.
3. Appliquer le schéma avant l’API et le client, puis vérifier les trois endpoints, les receipts, mouvements, journaux et révisions. Un schéma manquant provoque un 503 explicite et conserve l’intention ; aucun fallback de soustraction historique n’est activé.
4. Déployer l’API puis le web, mettre à jour le service worker et renouveler les anciens onglets. Les anciens bundles pouvaient écrire directement dans Supabase : un nouveau backend seul ne répare pas ces onglets. Vérifier séparément les anciennes routes REST si elles ont encore des consommateurs.
5. Exécuter les parcours matériels et fermer les critères d’acceptation avec leurs preuves et le SHA réel.

En cas d’incident d’intégrité, suspendre les writers concernés et présenter un état de lecture explicite. Pour les appels RPC directs, la suspension doit porter aussi sur les droits d’exécution en base, pas seulement sur la route HTTP. Conserver reçus, mouvements, journaux et identités de commande pour retrouver les résultats incertains. Réparer en avant ; ne pas supprimer ces tables ou redéployer les anciens transferts et snapshots absolus pour effectuer un rollback.

Le contrôle de versions d’annulation est volontairement conservateur : une modification ultérieure entraîne un conflit, même si certaines opérations pourraient être compensées après analyse. Les unités sans facteur connu et les ingrédients de quantité inconnue demandent une correction ou une déclaration explicite hors inventaire. Le matching de ce lot reste exact après normalisation ; les correspondances sémantiques et la confiance alimentaire enrichie relèvent des lots suivants.

## 9. Reproduire les contrôles

Depuis la racine `smart-pantry-pro` :

```sh
npm run build
npm run test:v10
```

Le test PostgreSQL crée une base unique `v10_test_<uuid>` et la supprime dans son `finally`. Il ne charge pas les fixtures dans une base existante et se connecte uniquement au socket local `/private/tmp/smart-grocery-v10-pg`, port 55438.

Pour un nouveau répertoire de test vide, avec PostgreSQL 16 Homebrew déjà installé :

```sh
/opt/homebrew/opt/postgresql@16/bin/initdb -D /private/tmp/smart-grocery-v10-pg --encoding=UTF8 --no-locale --auth=trust
/opt/homebrew/opt/postgresql@16/bin/pg_ctl -D /private/tmp/smart-grocery-v10-pg -l /private/tmp/smart-grocery-v10-pg.log -o "-h '' -p 55438 -k /private/tmp/smart-grocery-v10-pg" start
npm run test:v10:db
/opt/homebrew/opt/postgresql@16/bin/pg_ctl -D /private/tmp/smart-grocery-v10-pg stop
```

Ne pas réinitialiser un répertoire existant ; si celui de cette réalisation est conservé, démarrer simplement son serveur local. `V10_TEST_PSQL` permet de fournir le chemin d’un autre binaire PostgreSQL installé. Le schéma de test est [v10-schema.sql](../../supabase/tests/v10-schema.sql).

Pour le contrôle visuel isolé :

```sh
npm run test:v10:ui
```

Ouvrir `http://127.0.0.1:5174/scripts/fixtures/v10/index.html`. Les données en mémoire sont réinitialisées à chaque rechargement. Le bouton « Simuler une coupure » ne constitue pas une injection d’erreur de base réelle : les tests PostgreSQL apportent cette preuve indépendante.

Le lint ciblé est reproductible sur les mêmes fichiers :

```sh
python3 - <<'PY'
import json, subprocess
from pathlib import Path
files = [row['file'] for row in json.loads(Path('docs/implementations/v10-01/lint.json').read_text())['results']]
subprocess.run(['npx', 'eslint', *files], check=True)

```
