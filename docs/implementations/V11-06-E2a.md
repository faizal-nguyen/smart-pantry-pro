## 1. Constat de départ

Relevé sur `main` (`ec491cbb`) :
- **Deux piles montées** dans `App.tsx` et dans le banc V10 : Radix (`<Toaster />`) et Sonner.
  - Radix : 21 fichiers de production appelaient `@/hooks/use-toast`, 72 appels dont 40 en `variant: 'destructive'`. La PRP en comptait 23, en incluant `toaster.tsx` et le contexte de session, qui ne faisait que purger.
  - Sonner : 5 appelants.
  - Aucun appel n'utilisait d'action, de durée, d'identifiant ni de mise à jour.
- **Les notifications recouvraient la barre basse** :
  - à 390 px, Sonner applique sous 601 px sa marge mobile par défaut de 16 px, alors que la barre mesure environ 73 px plus la zone de sécurité ;
  - à 899 px, la marge reposait sur `--content-bottom-pad`, qui tombe à 1,5 rem dès 768 px alors que la barre reste affichée jusqu'à 900 px ;
  - passée en chaîne, cette marge s'appliquait aussi aux quatre côtés : décalage de 40 px depuis la droite sur grand écran.

| Réglage | Valeur | Raison |

**Règle de conversion des appels**

| Avant | Après |
| --- | --- |
| `toast({ title, description })` | `toast(title, { description })` |
| `toast({ title, description, variant: 'destructive' })` | `toast.error(title, { description })` |
| `const { toast } = useToast()` | `import { toast } from 'sonner'`, sans hook ; `toast` quitte les dépendances des callbacks |

## 4. À signaler

- **Barres collantes au-dessus de la barre basse.** Le résumé des courses, les notices des menus et la barre d'action de la fiche recette (z-index 30) se placent juste au-dessus de la barre basse sous 900 px. Une notification peut les recouvrir le temps de son affichage. La PRP exige seulement de ne pas recouvrir la barre basse.
- **`--content-bottom-pad`** vaut 1,5 rem dès 768 px alors que la barre reste affichée jusqu'à 900 px. Les notifications n'en dépendent plus, mais `.app-content` et quelques marges de défilement l'utilisent encore. Le commentaire « Sur md+ (>= 768px) la sidebar prend le relais » de `index.css` est obsolète.
- **`ResponsiveContext.navHeight`** lit la hauteur théorique (`--mobile-nav-height`, nulle dès 768 px), et non la hauteur mesurée.
- **`RecipeOnboarding`** déclenche une notification d'erreur depuis une fonction de mise à jour d'état. Ce défaut existait déjà avec Radix et la conversion le reprend tel quel. En mode strict de développement, la fonction s'exécuterait deux fois ; le remplacement n'en laisse qu'une visible.
- Le composant accepte encore des propriétés. Passer `toastOptions` remplacerait tout l'objet, styles d'erreur compris. Aucun appelant n'en passe.

## 5. Relecture

Une relecture indépendante (`typescript-reviewer`) a lu le diff de la branche commit par commit et relancé 32 suites de tests. Aucun constat critique ni élevé.

**Vérifié, sans problème**
- **Conversions fidèles** dans les 21 fichiers : aucun texte ni aucune description perdus ; la variante rouge devient toujours `toast.error`. Aucun appelant n'utilisait la valeur renvoyée, un identifiant, une action ni une mise à jour.
- **`AssistantActionsPanel`** : les quatre issues sont correctes. Appeler `toast.error` sans son objet est sûr dans Sonner 1.7.4 : c'est une fonction fléchée liée à l'instance.
- **Dépendances de `useSpeechRecognition`** : `toast` en sort à juste titre, l'import étant stable.
- **Plus aucun importeur ni aucune simulation** des modules supprimés. Les simulations de `sonner` restantes sont appelables là où le code appelle `toast(...)`.
- **Verrou** : seule l'entrée `@radix-ui/react-toast` est retirée.
- **Purge au changement de compte** : correcte, et le test la prouve.
- **Spécificité des classes d'erreur** : elles l'emportent sur les couleurs neutres (0,3,0 contre 0,2,0), et les styles de Sonner sont de spécificité nulle.
- **Chaque commit est cohérent seul.**

**Étapes**, avec l'accord de l'utilisateur :
